PDP Tabs — Aligned to the Page Grid

Four changes to the tab area, what went back to the theme default, and five things I need you to decide

21 September 2026MDM Shopify themeKonrad Thiemann

Three days ago we straightened the product block on the detail page so it lines up with the breadcrumbs. The tab area below it still had a page grid of its own, so the same misalignment was still there — just lower down the page. That is now fixed, along with three other things you asked for. One of them changes how text looks, and that is the part I would like you to look at first.

1. The four changes

Anything we change in a theme sits on one of five layers, from the theme’s own behaviour at the top to a rule typed into the theme editor at the bottom. The further up a change sits, the less of it is ours to maintain. Section 6 explains the layers in full; the last column here is the short answer for each change.

3. The reading column: 700 → 760 px

STAYS ON LAYER 4 · SECTIONhand-set in this section — a deliberate exception, the only one left

The description and the free-extras tab are held to a fixed reading width so the lines do not run the full width of a large screen. That column is now 760 px instead of 700 px, as you asked. It takes effect from 1280 px upward; below that the window is narrower than the column anyway, so nothing changes on phones and tablets.

The technical data table is deliberately not inside this column — see section 5.

4. Text styling — the change you will notice

NOW ON LAYER 2 · BRANDour shop-wide rich-text stylesheet — shared with every other page

This section used to carry its own type scale, written directly into it. That is now gone, so the text in the tabs is styled by the same shop-wide rich-text rules that already style the help pages, the policy pages and every other body copy in the shop.

On desktop the body copy is practically unchanged. The headings inside the description are not — they used to render as a small uppercase eyebrow line, and now render as a real heading.

Worth knowing: “theme default” here means two different things

The page grid went back to the theme’s own stylesheet — that is a true restoration of the Nexvo default.

The typography went back to our brand layer, the file that sits on top of the theme and carries the MDM type scale and colours. That is still our own design, just defined once for the whole shop instead of separately inside this one section. Nexvo untouched would look different again.

Read down the “where it comes from” column and the picture is this: the tab area is mostly Nexvo underneath, with roughly a dozen hand-set rules on top. Eleven of those left with this change, one was adjusted to your 760 px, and what remains is brand styling — colours, type sizes and spacing — rather than layout.

One override you should know about: the bottom spacing

The theme editor has a control for the space below this section, and it is set to 0 px. The section ignores it: a hand-set 60 px in the code wins, and I measured 60 px on the page. So turning that dial in the editor does nothing.

I left it as it is, because removing it would collapse the gap to the section below and that is a spacing decision, not a cleanup. But it is exactly the kind of thing that makes the editor feel broken — see D5.

7. Five decisions for you

  1. The headings inside the description This is the real question in this document. Those lines used to be a small uppercase eyebrow — a deliberate choice from the Figma file, noted in the code. Letting the theme settings drive the text means that choice goes away and they become EB Garamond 32 px in navy, like headings everywhere else in the shop. Both are defensible. If you want the eyebrow back, it comes back as a section-level exception, and we should write down why — otherwise it is exactly the kind of override that is invisible later.
  2. That heading is 32 px on phones too The shop-wide rule has no separate phone size for this heading level, so a 375 px screen gets a 32 px heading. It was 11 px before. If that is too large, the fix belongs in the shop-wide type scale rather than in this section — it would fix the help pages at the same time.
  3. Body copy on phones grew from 14 to 16 px A direct consequence of dropping the section’s own sizes. 16 px is the shop-wide body size and, for what it is worth, the friendlier of the two to read. Just confirming you are happy with it, because it is a visible change on every product page.
  4. Wide screens: the table rules now run long Each of the two table columns is 785 px wide at 1920 px, but the widest row only uses 326 px of it. So the hairline under each row carries 459 px of empty space — it was 274 px before, so the change made an existing effect more visible. Either the two columns should not grow past a sensible maximum, or the rules should stop where the text stops. This is a design call, not a bug.
  5. Should the bottom spacing go back to the editor? The box in section 6: the space below this section is hand-set to 60 px in the code and the editor control for it is dead. I can release it, and then the value you set in the editor is the value on the page — but the current 0 px in the editor would make the gap collapse, so we would need to put 60 px in first. Small job, your call whether it is worth doing now or with the next round of spacing work.

8. One observation outside the layout

On the test product several rows in the technical data table have no label at all — “Silber (900/1000)”, “10000”, “2026” and “50.00” sit there on their own. That is product data, not layout: the label fields on the product are empty. Flagging it because it will show up in any screenshot you take of this tab, and it is not something the theme can fix.

One rule is still stored in the section’s Custom CSS field in the theme editor, not in the code: .image-with-text__content { max-width: 52rem }. It has no effect on the tabs as they are built today, because the block it targets is not in use. It would take effect the moment someone adds an image-with-text block to this section.
