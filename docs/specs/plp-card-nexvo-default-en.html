2. Why the theme editor does nothing

This is the part that matters most for you. The settings are still there and still switched on — the card simply never reads them.

One collision to resolve before we restore the hover

Nexvo uses the second product image for the hover reverse — the effect you said should stay. Latori uses the same images (images 2 to 4) for the round “Weitere Ausgaben” thumbnails.

So if we switch the hover back on and leave the thumbnails as they are, the second image will appear twice: once as the hover reverse, once as the first thumbnail. We need to decide which one wins — see C2.

4. The five decisions — our agenda

  1. Whole tile clickable This was the request I started from before our call, so I want to put it to you honestly: it is not a Nexvo default. The original card also has only an image link and a title link. Making the whole tile clickable would be a deliberate addition on top of the default, not a restoration of it — which sits awkwardly next to “we don’t want to override anything here”. My suggestion: restore the default first, then look at the card again and decide whether it still needs it.
  2. The “Weitere Ausgaben” thumbnails You said they are presentation only, with no function. Two questions. Do we take their links off and leave them decorative, or remove them altogether? And once the hover reverse is back, which of the two shows the second image — see the box above.
  3. The “KOLLEKTION · Classic / Flatrate / Set” badge Latori invented this; it is not on the list of things we ordered and the labels are written straight into the code. Keep it, drop it, or rebuild it properly from product data?
  4. Two implementations of the 30-day price The collection card reads the metafield directly; the compact card used elsewhere uses a shared component. Same legal line, two mechanisms. Which one is the right one?
  5. How far does the restore go? Restoring the default brings back quick-view, quick-add and the compare checkbox. That is a visible change to the collection page. Confirm you want them, or we switch the individual ones off through the settings — which is the clean way, because then it stays visible in the editor rather than buried in code.

5. How we avoid overwriting each other

You work in the theme editor, I work in the code and open pull requests. Worth knowing: the store and the repository are synced in both directions, so your theme editor changes do arrive in the code repository as automatic commits — there are three from 7 September in the history already. They mostly touch the settings file.

That is good news: it means we are not on separate islands. It also means I need to pull your changes before I push mine. If we both touch the same thing, we look at it together and pick one, exactly as we said.

“But if you override everything, then we won’t know later what has to be removed.” — that is the principle this whole document is built on. Anything we change from here should go through a setting. Code only where no setting exists, and written down when it happens.
