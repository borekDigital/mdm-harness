Blatt 01/04

Routing über Basisklassen

In messenger.yaml stehen drei Routing-Regeln, und jede nennt eine abstrakte Basisklasse. Symfony ordnet eine Nachricht dem Transport zu, wenn ihre Klasse von der genannten erbt. Das ist der Grund, warum ein neuer Mailtyp keine Änderung an dieser Datei braucht.

www/config/packages/messenger.yaml:9–12
routing:
  'App\Queueing\Messages\Requests\Sap\Mailing\Base\IncomingMailRequest': incoming_mail_requests
  'App\Queueing\Messages\Requests\Sap\Enrichment\Base\EnrichmentRequest': enrichment_requests
  'App\Queueing\Messages\Requests\Emarsys\Base\EmarsysEventRequest':      emarsys_event_requests
Blatt 02/04

Der Weg einer Mail — vier Stationen

Zwischen dem SAP-Aufruf und der Mail bei Emarsys liegen vier Stationen und drei Warteschlangen. Nur die erste läuft im Request; die Antwort an SAP geht raus, sobald Station 1 eingestellt ist.

Blatt 04/04

Kundendaten kommen jetzt von Emarsys

Ohne den SAP-Pfad ist der Dienst nicht datenlos — er bezieht die Kontaktdaten aus der Gegenrichtung. EmarsysEventHandler fragt sie bei Emarsys ab, bevor er das Event auslöst.

www/src/Queueing/Handler/Emarsys/EmarsysEventHandler.php:72–78
$emarsysContactDataResponse = $this->emarsysService->getEmarsysContactData($emarsysEventRequest);
$emarsysContactData = $emarsysContactDataResponse->getData()->getResult();
if (is_array($emarsysContactData) && array_key_exists(0, $emarsysContactData)) {
    $emarsysEventRequest->setEmarsysContactData($emarsysContactData[0]);
}

Die dokumentierte und die tatsächliche Datenquelle unterscheiden sich also — mit Folgen für die Frage, wer die Werbesperre auswertet. Im Code tut es niemand; ob Emarsys eine eigene Unterdrückungsliste führt, ist von hier aus nicht feststellbar.

01

Der Opt-out-Filter läuft nicht

Beleg: MailBarrierTask::check prüft $data->isMailAllowed() && !$data->isMailBlocked(). Der Task hängt am PaymentReceivedValidator, dieser am ValidationService, dieser wird allein aus EnrichmentService.php:68 aufgerufen — und performEnrichment hat nur den auskommentierten Aufrufer in EnrichmentHandler.php:65.

Konsequenz: Kunden mit Werbesperre werden im Code nicht ausgefiltert. Ob im Betrieb trotzdem keine Mail rausgeht, entscheidet allein Emarsys.

⚠️ Offene Frage: Führt Emarsys je Mandant eine Unterdrückungsliste, die die SAP-Sperre abbildet? Nur mit Emarsys-Zugang prüfbar. Vor einer Reaktivierung des Pfades zu klären.

02

ValidationService erkennt einen fehlenden Validator nicht

Beleg: www/src/Services/Sap/Validation/ValidationService.php:52–64 setzt $validator = null, benutzt dieselbe Variable dann als foreach-Laufvariable und prüft danach if ($validator === null). Nach einer Schleife über ein nicht leeres Array hält die Variable das letzte Element — nie null.

Konsequenz: ValidationException::MISSING_VALIDATOR greift nur, wenn überhaupt kein Validator registriert ist. Registriert ist genau einer (PaymentReceivedValidator), also würde jedes andere Ereignis die Validierung stillschweigend überspringen, statt zu scheitern — auch nach Reaktivierung des Pfades aus Blatt 03.

Fix: eine eigene Trefferschleifenvariable, oder return im Trefferfall und throw dahinter.

03

Es gibt keinen failure_transport — endgültig gescheiterte Nachrichten sind weg

Beleg: www/config/packages/messenger.yaml definiert drei Transporte und drei Busse, aber weder failure_transport noch retry_strategy. Es gilt die Symfony-Voreinstellung: drei Versuche, danach verwerfen.

Konsequenz: Eine Mail, deren Emarsys-Aufruf dreimal scheitert, ist verloren und nicht nachstellbar — es gibt keine Datenbank und keine Fehlerwarteschlange, aus der man sie erneut anstoßen könnte. Bei gesetzter maintenance.flag trifft das jede Nachricht im Retry-Fenster.

Fix: einen vierten Transport failed anlegen und als failure_transport eintragen. Danach steht messenger:failed:retry zur Verfügung.

04

Sechs Stamps, davon zwei ohne erkennbaren Setzer

Beleg: www/src/Queueing/Stamps/ enthält DoNotSendStamp, EnrichedMailDataStamp, ErrorStamp, MessageReceivedStamp, ValidationPassedStamp und die Basisklasse AbstractStamp. Gesetzt wird in den Middlewares der Symfony-eigene ValidationStamp, nicht diese.

Konsequenz: DoNotSendStamp und EnrichedMailDataStamp gehören zum abgetrennten Pfad aus Blatt 03 — sie sind die Marker, mit denen ein gefilterter oder angereicherter Datensatz durch die Kette getragen würde. Wer den Pfad reaktiviert, braucht sie; wer den Code aufräumt, darf sie nicht mit dem Rest wegwerfen.
